# Версии и GitHub Releases

[Русский](releases.md) · [English](en/releases.md) · [Все документы](README.ru.md)

Единственный источник версии — `Sources/BufferaCore/AppVersion.swift`:

- `version`: стабильная версия `MAJOR.MINOR.PATCH`, без `v`, суффиксов и ведущих нулей;
- `build`: положительный целый номер сборки, увеличивающийся при каждом выпуске, в том числе при смене версии.

Обе строки читаются `scripts/version.sh`, поэтому сохраняйте формат строковых констант. Приложение получает их в `CFBundleShortVersionString` и `CFBundleVersion`; MCP использует ту же версию непосредственно из BufferaCore. Номер версии также виден в Finder → «Свойства» приложения.

Исправления увеличивают PATCH, новые возможности — MINOR, несовместимые крупные изменения — MAJOR. При увеличении MINOR обнуляйте PATCH; при увеличении MAJOR обнуляйте MINOR и PATCH. Номер `build` никогда не сбрасывайте. Поддерживаются только стабильные выпуски.

## Подготовка

1. Измените `version` и увеличьте `build` в `AppVersion.swift`.
2. Добавьте описание изменений и установки в `docs/releases/X.Y.Z.md` на всех восьми поддерживаемых языках. Обновите все языки `docs/INSTALL.txt`, если меняется установка; сверяйте названия кнопок с каталогами приложения. Пример структуры — [1.0.0](releases/1.0.0.md).
3. Проверьте изменения и выполните соответствующие проверки приложения. Проверьте сборку и пакет:

   ```sh
   export BUFFERA_NOTARY_PROFILE=YOUR_KEYCHAIN_PROFILE
   zsh scripts/build-app.sh
   zsh scripts/package-release.sh
   zsh scripts/notarize-release.sh
   zsh scripts/create-appcast.sh
   zsh scripts/check-signing.sh
   zsh scripts/check-notarization.sh
   zsh scripts/check-appcast.sh
   zsh scripts/check-release.sh
   ```

   Упаковщик откажется упаковывать `.app`, если его версия или сборка отличаются от исходников.
   `check-release.sh` проверяет ограничения выпуска в одноразовом репозитории с подставным GitHub CLI, без сетевых запросов и публикаций.
   Дождитесь успешного завершения каждой проверки: отдельные строки PASS не подтверждают успех всего запуска.

4. Закоммитьте подготовленный выпуск. Убедитесь, что в коммит не попали локальная история, модели, архивы поддержки или ключи.
5. Создайте аннотированный тег `vX.Y.Z` на этом коммите и отправьте коммит и тег в GitHub. Пример для `0.2.0`:

   ```sh
   git tag -a v0.2.0 -m 'Buffera 0.2.0'
   git push origin HEAD
   git push origin v0.2.0
   ```

## Создание и публикация релиза

На Apple Silicon Mac со Swift 6.4+, настроенной Developer ID identity, существующим профилем `notarytool` в Keychain и авторизованным GitHub CLI:

```sh
BUFFERA_NOTARY_PROFILE=YOUR_KEYCHAIN_PROFILE zsh scripts/create-release.sh
```

Скрипт проверит чистоту отслеживаемых файлов, соответствие локального и удалённого тегов текущему `HEAD`, а также отсутствие релиза с таким тегом. Затем распакует **только содержимое коммита** во временную папку и последовательно выполнит сборку, упаковку, нотарификацию DMG и создание подписанного appcast. Неотслеживаемые локальные файлы в сборку не попадут. Для среды, запрещающей вложенный sandbox SwiftPM, поддерживается `--disable-sandbox`.

Результат сохраняется в `dist/releases/vX.Y.Z/`, затем создаётся **черновик** GitHub Release с тремя вложениями:

- `Buffera-macOS-arm64.dmg`;
- `appcast.xml` — подписанный канал с подписью DMG и встроенными примечаниями;
- `SHA256SUMS.txt` — контрольные суммы DMG и appcast.

Релизный скрипт явно использует `--build-system native`, как проверки интерфейса. В конфигурации только с Command Line Tools другая система сборки может записать минимальную версию macOS вместо версии SDK и тем самым изменить режим совместимости и геометрию контролов AppKit. Проверяйте итоговый DMG, а не только локальную сборку приложения.

Имя DMG остаётся постоянным: ссылки сайта и README на `releases/latest/download/Buffera-macOS-arm64.dmg` продолжат работать после публикации нового latest-релиза.

Проверка обновлений в приложении использует публичный `/repos/dqunbp/buffera/releases/latest`. Она сравнивает стабильный тег `vX.Y.Z` (или `X.Y.Z`) с `AppVersion.version` и предлагает только более новую версию с готовым ненулевым `Buffera-macOS-arm64.dmg` по ожидаемому адресу этого тега. Черновики, prerelease, неподдерживаемые теги, чужие адреса и незавершённые вложения не предлагаются. Повторная сборка с тем же тегом не считается обновлением, поэтому опубликованные выпуски не заменяются. Подробности интерфейса — в [руководстве](guide.md#обновления).

Откройте черновик в GitHub, проверьте описание, наличие всех трёх вложений, установку DMG и обновление с предыдущей версии. Опубликуйте через **Publish release**, назначив выпуск Latest. Черновик не меняет текущий публичный latest-релиз. Поведение `--draft` и `--verify-tag` описано в [документации GitHub CLI](https://cli.github.com/manual/gh_release_create).

Если сеть или сборка недоступны, скрипт завершится с ошибкой до создания релиза. Ошибка загрузки вложений может оставить частичный черновик: проверьте его в GitHub и добавьте отсутствующие файлы из `dist/releases/vX.Y.Z/`. Повторный запуск не перезаписывает существующий релиз. Опубликованные теги и вложения не заменяйте: для исправлений выпускайте новую версию и сборку.

## Подпись и ограничения скриптов

`scripts/signing.sh` задаёт общую подпись для `build-app.sh`, `prepare-model-runtime.sh` и `create-release.sh`. Без настройки используется ad-hoc. Для Developer ID Application импортируйте сертификат, соответствующий закрытому ключу в вашей Связке ключей, и найдите его SHA-1:

```sh
security import /path/to/developerID_application.cer -k "$HOME/Library/Keychains/login.keychain-db"
security find-identity -v -p codesigning
BUFFERA_SIGNING_IDENTITY=YOUR_40_CHARACTER_SHA1 zsh scripts/build-app.sh --build-system native
```

Для постоянной настройки запишите только SHA-1 одной строкой в `output/developer-id/signing-identity.txt` (папка исключена из Git). Переменная `BUFFERA_SIGNING_IDENTITY` имеет приоритет; значение `-` явно включает ad-hoc. Не сохраняйте здесь закрытый ключ или пароль. Выбранная Developer ID identity должна быть действующей и иметь закрытый ключ; иначе сборка остановится до компиляции. Отказ доступа к ключу, ошибка подписи или временной метки также останавливают сборку без отката к ad-hoc. macOS может запросить разрешение `codesign` на использование ключа.

Developer ID применяется к библиотекам llama.cpp, трём модельным утилитам, MCP, Sparkle (Autoupdate → Updater.app → framework) и приложению, от вложенных компонентов к внешнему пакету. Все получают защищённую временную метку Apple (нужна сеть); исполняемые файлы — Hardened Runtime. Исключения Hardened Runtime не добавляются. `create-release.sh` передаёт выбранную identity в изолированную сборку через окружение: локальный файл настройки и сертификат в архив исходников не включаются. Порядок и параметры соответствуют [инструкции Apple](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/).

`build-app.sh` собирает пакет во временной папке, подписывает и проверяет его там, затем копирует без служебных атрибутов в `dist/Buffera.app` и проверяет ещё раз. Это исключает повторное добавление FinderInfo файловым провайдером Documents во время подписи. Провайдер всё ещё может изменить атрибуты результата позднее; рабочую копию держите вне синхронизируемой папки.

Проверки скриптов: `zsh scripts/check-signing.sh`, `zsh scripts/check-notarization.sh` и `zsh scripts/check-release.sh` (фикстуры, без настоящих ключей и публикации). Проверки готового артефакта:

```sh
codesign --verify --deep --strict dist/Buffera.app
codesign -dvvv dist/Buffera.app
```

В Developer ID сборке проверьте `Authority`, `TeamIdentifier`, `Timestamp` и флаг `runtime`; отдельно проверьте вложенные исполняемые файлы и dylib. Подпись не выполняет нотарификацию Apple и не устанавливает обновление. Перед утверждением о подписи установленного или опубликованного приложения проверьте именно этот артефакт. Переход с ad-hoc может потребовать повторного разрешения доступа к существующему ключу истории; сохранение доступа после обновления проверяется отдельно, без сброса ключей или истории.

В `scripts/create-release.sh` сохраняйте последовательное создание архива и его распаковку. На macOS `tar` может завершиться, не прочитав завершающее заполнение архива, из-за чего потоковый конвейер `git archive | tar` завершается с SIGPIPE (141) при включённом `pipefail`. Сначала полностью запишите архив в файл, затем распакуйте его; реальные ошибки обоих этапов должны прерывать выпуск. `scripts/check-release.sh` содержит регрессионные проверки задержанного заполнения архива, ошибки создания архива и ошибки распаковки.

## Нотарификация выпуска

`scripts/notarize-release.sh` требует Developer ID и переменную `BUFFERA_NOTARY_PROFILE` с именем уже настроенного профиля `notarytool` в Keychain. Пароли, API-ключи и имя локального профиля в исходники не добавляются. `create-release.sh` передаёт профиль изолированной сборке; отсутствие профиля останавливает выпуск до сборки и загрузки в GitHub.

Скрипт проверяет исходную контрольную сумму DMG, подписывает образ Developer ID с timestamp и отправляет его через `xcrun notarytool submit --wait --timeout 20m --output-format plist`. Только успешный ответ `Accepted` разрешает продолжение. Затем `stapler` прикрепляет и проверяет билет DMG; `codesign` и Gatekeeper проверяют сам образ и приложение, смонтированное непосредственно из этого образа. Номер версии и сборки внутри DMG также должен совпасть с исходниками. Билет прикрепляется к распространяемому DMG; отдельный stapling внутреннего `.app` этот шаг не выполняет. Процесс соответствует [порядку Apple](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).

Подпись и stapling меняют байты DMG, поэтому SHA-256 пересчитывается после всех проверок, а appcast генерируется последним. Нельзя менять образ после подписи Sparkle. Любая ошибка нотарификации, stapling, проверки подписи или Gatekeeper прерывает создание релиза.

Ответ Apple, идентификатор задания и доступный диагностический журнал сохраняются по отдельной папке попытки в `dist/releases/vX.Y.Z/notarization/` и не удаляются вместе с временной сборкой. При отдельном запуске путь по умолчанию — `dist/notarization/vX.Y.Z/`, его можно изменить через `BUFFERA_NOTARY_LOG_DIR`. После тайм-аута Apple может продолжать обработку: сначала проверьте уже выданный идентификатор через `notarytool info`/`log`, не отправляйте повторные задания вслепую. Эти локальные журналы не входят во вложения GitHub Release.

## Установка обновлений через Sparkle

`UpdateInstaller.swift` запускает Sparkle 2.10.1 только по кнопке «Обновить…». Фоновые проверки по-прежнему принадлежат `UpdateChecker`: настройка автоматической проверки, суточный интервал, пропуск и индикаторы общие. Пропуск в окне Sparkle передаётся тому же checker. Sparkle не получает историю, не отправляет системный профиль и не устанавливает обновления без действия пользователя.

`build-app.sh` включает `Sparkle.framework` и лицензию, задаёт rpath в Package.swift и подписывает вложенные компоненты до приложения. Неиспользуемые XPC Services удаляются, поскольку Buffera не sandboxed. В Info.plist отключены автоматические проверки/установка Sparkle, включены `SUVerifyUpdateBeforeExtraction` и `SURequireSignedFeed`; истечение проверки подписи канала отключено. Поле `SUPublicEDKey` берётся из отслеживаемого `scripts/sparkle-public-key.txt`.

Закрытый Ed25519-ключ находится в login Keychain под account `local.buffera.app`. Он не является сертификатом Developer ID; для выпуска нужны оба ключа. Инструменты приходят из закреплённого SwiftPM-артефакта `.build/artifacts/sparkle/Sparkle/bin`. На другой машине импортируйте сохранённый ключ штатными `generate_keys -x` / `-f`, не создавайте другой вместо потерянного. Экспорт — секрет: храните его вне репозитория в защищённом хранилище. Не изменяйте правила доступа Keychain для обхода запроса macOS.

`create-appcast.sh` сверяет публичный ключ Keychain с репозиторием и собранным приложением, проверяет SHA-256 готового DMG, запускает официальный `generate_appcast` с этим account, проверяет подпись канала и версию/сборку из архива. Временная папка содержит только один выпуск, дельты выключены. Генерация может запросить доступ к ключу в Keychain. Ошибка прерывает выпуск до загрузки в GitHub.

Канал публикуется **в том же релизе**, что и DMG, по адресу `https://github.com/dqunbp/buffera/releases/download/vX.Y.Z/appcast.xml`. Поэтому публикация черновика открывает оба файла одновременно; отдельный деплой сайта не нужен. Установщик фиксирует выбранный тег и проверяет соответствие версии и URL DMG. Нельзя редактировать подписанный XML или DMG после генерации; выпустите новую версию. Черновик с недостающим appcast не публикуйте.

Проверка версии и URL повторяется в пользовательском драйвере Sparkle перед показом возобновлённого обновления: старый загруженный архив или отложенная установка отменяются, если они не соответствуют выбранному релизу. Такой отказ не помечает выбранный релиз пропущенным; установка доступна для повторной попытки.

Первый выпуск с установщиком нужно поставить вручную: опубликованная 0.4.0 не содержит Sparkle. Перед публикацией проверьте переход между двумя отдельными установленными подписанными сборками: загрузку, отказ при повреждении подписи, отмену, замену, перезапуск и сохранность истории/доступа к Keychain. Автоматические UI-проверки используют подставной установщик и не доказывают успешную замену приложения. Нотарификация DMG в релизном конвейере также не доказывает замену приложения: для проверки политик macOS нужен переход между нотарифицированными сборками.

Проверки: `zsh scripts/check-appcast.sh`, `zsh scripts/check-release.sh`, `zsh scripts/check-signing.sh`, `zsh scripts/check-notarization.sh`, `swift run BufferaUpdateChecks` и `Buffera --updates-ui-smoke-test` на всех поддерживаемых языках. Официальные контракты: [Sparkle setup](https://sparkle-project.org/documentation/), [settings](https://sparkle-project.org/documentation/customization/), [code signing](https://sparkle-project.org/documentation/sandboxing/).
